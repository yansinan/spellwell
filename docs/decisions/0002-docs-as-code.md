# ADR-0002：让设计文档贯穿开发过程（docs-as-code）

- **状态**：Accepted
- **日期**：2026-11-11
- **决策者**：项目初始化（P0）
- **影响条款**：DESIGN §四、§八；FILE_SPEC §10/§11

## 背景

项目文档很长，且明确“定稿”。实际开发中常见失效路径：

- 文档放在聊天记录或外部网盘，agent 每次只看到局部需求，逐渐按“方便实现”走样。
- 代码里出现设计没写的功能（积分、连胜、自动切分），评审时才发现。
- 测试只测“代码能跑”，不测“设计约束有没有被违反”。
- 阶段推进靠感觉，P0 没绿就开始写 P3。

## 决定

把 DESIGN 作为仓库内的**唯一需求源**，并用五层机制让它持续生效：

1. **唯一源 + 版本**：`docs/DESIGN.md` 入库，标注版本、状态、变更控制；任何偏离先写 ADR。
2. **条款锚点 + 追溯矩阵**：DESIGN 使用 `§x.y`；`docs/TRACEABILITY.md` 把每条可执行规则映射到代码路径、验证方式、阶段、状态。
3. **代码头注释**：每个 `src/**/*.js` 必写 `@layer/@phase/@doc`；`@doc` 必须指向真实小节，`traceability.test.js` 校验。
4. **架构守卫测试**：把铁律写成 `tests/p0/architecture.test.js`：
   - 无 `Math.random`；
   - 题型层不 import 存储/仓库/UI；
   - 调度层不碰 DOM；
   - 仓库层只用 adapter 白名单方法；
   - 层目录与 `@layer` 一致；
   - 无循环依赖。
5. **阶段门禁**：`tests/runTests.js --phase=pN` 累计运行 `p0..pN`，输出 PASS/FAIL；`ROADMAP.md` 维护阶段状态；`AGENTS.md` 规定 agent 必读顺序与完成定义。

## 后果

- 正面：
  - 新 agent 只需读 `AGENTS.md` → DESIGN → TRACEABILITY → ROADMAP，就能在不追问的情况下接手。
  - 违反架构的代码在 `--phase=p0` 就会失败，而不是等到联调。
  - 设计变更留下 ADR 历史，不会出现“文档说 A、代码做 B”且无人知道为什么。
  - 测试名称/追溯矩阵让“这条规则谁负责”可查。
- 负面：
  - 写规则要同时写测试，前期比“先跑起来”慢。
  - 文档更新有成本；为此把文档拆成 DESIGN（为什么/是什么）与 FILE_SPEC/TRACEABILITY/ROADMAP（怎么做/谁验证），避免一份文件无限膨胀。
  - 静态守卫可能误伤，需要 ADR 或白名单，而不是直接删测试。

## 具体运行方式

| 时机 | 动作 |
|---|---|
| 开始任一阶段 | 读 `AGENTS.md` → 当前阶段任务书 → 相关 TRACEABILITY 行 |
| 写新文件 | 先写 `@layer/@phase/@doc` 头，再写实现 |
| 跨层数据 | 先在 `contracts.js` 加类型/校验，再加测试 |
| 完成功能 | 跑 `--phase=pN`；更新 TRACEABILITY 状态；更新 CHANGELOG |
| 必须偏离 DESIGN | 写 ADR（背景/决定/后果/否决方案），更新 DESIGN 版本与 TRACEABILITY |
| 阶段验收 | 人工确认 👁 项；ROADMAP 标完成；写下一阶段任务书 |

## 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 只把文档放 README | 太长、无条款锚点，无法逐条追溯 |
| 用注释代替测试 | 注释不会失败，三个月后无人遵守 |
| 引入 lint 工具/框架做守卫 | 违背“无构建、无依赖”；Node 脚本足够 |
| 每个阶段重写一份设计 | 版本漂移，历史决策丢失 |
| 让 agent 自由发挥，最后人工对文档 | 返工成本最高，且会悄悄引入被剔除的功能 |
